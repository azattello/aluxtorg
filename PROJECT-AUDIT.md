# Аудит готовности интернет-магазина

**Дата проверки:** 16 ноября 2026  
**Основание:** требования в `copilot-ecommerce-prompts/docs/`, acceptance checklist, roadmap, API-маршруты и фактические экраны приложения.  
**Общий статус:** каталог, аккаунты, аутентифицированный checkout, CRM и склад реализованы частично. Добавлены русские API-ошибки, вход по телефону/email, необязательный email при регистрации, брендированная рекламная главная, настраиваемые контакты магазина и first-party статистика. Новые миграции применены к локальной SQLite-базе, используемой dev API; новые миграции и concurrency-сценарии PostgreSQL повторно проверить нельзя, так как активный PHP CLI не имеет `pdo_pgsql`, а локальных DLL расширения нет. Юридическая проверка, данные для контактов и operational hardening остаются launch-блокерами.

## Краткий вывод

Текущее приложение не соответствует требованию «все экраны, кнопки и функции работают» для целевого проекта. Работают аутентификация, публичный каталог и отдельные операции управления каталогом. Добавлены клиентский сценарий корзина → checkout → сохранение заказа → подтверждение и история заказов, а также менеджерская очередь/карточка, назначение сотрудника, внутренние заметки, стоимость доставки, статусы заказа/оплаты и история действий.

CRM теперь позволяет сотрудникам с утверждёнными ролями фильтровать и искать заказы, открывать детали, назначать ответственного, добавлять приватные заметки и обновлять допустимые статусы. Подтверждение атомарно резервирует остатки; отмена освобождает активный резерв; отгрузка и завершение самовывоза списывают его без повторного списания. Складской экран/API поддерживает поиск остатков/SKU, поступления, сверку физического количества и журнал движений; глобальный порог 2 доступные единицы показывает низкие остатки и запускает Telegram-сообщение при пересечении порога вниз.

### Прогоны и ограничения проверки

- Frontend: `npm run build` — **успешно** (TypeScript и Vite production build).
- Initial JS entry после code splitting — около **231 kB / 73 kB gzip**; страницы админки загружаются отдельными чанками.
- Backend SQLite: полный PHPUnit suite — **91 passed, 8 skipped, 99 всего, 567 assertions**. PostgreSQL-only concurrency tests пропускаются в SQLite-конфигурации.
- Локальные migrations применены; dev API (`127.0.0.1:8000`) отвечает HTTP 200 для категорий, товаров и публичных настроек магазина. Некорректный диапазон цены отвечает HTTP 422 с русским сообщением.
- Backend PostgreSQL: предыдущая версия прошла **4 tests, 29 assertions** три раза подряд в `ecommerce_qa_concurrency`. Повторный запуск после новой migration заблокирован: PHP CLI сообщает `could not find driver`; `php_pdo_pgsql.dll` и `php_pgsql.dll` отсутствуют в активной PHP `ext` папке. Не направлять `migrate:fresh` на другую схему/базу в обход этой проверки.
- В backend зарегистрировано 47 прикладных API routes. CRM, склад и управление ролями защищены server-side role checks.
- Frontend: все Playwright E2E — **7 passed**: поиск/фильтр/сортировка и смена роли, виды карточек/таблицы для пользователей, заказов и возвратов, мобильные вкладки, demo hero, отсутствие горизонтального переполнения каталога и подача заявки на возврат; API стабилизирован mocks. Сквозные order checkout, CRM order workflow и warehouse E2E, keyboard/accessibility audit и unit/component suite ещё не покрыты.
- CLI-сообщения команды назначения первого супер-администратора и сообщение правила `gte` переведены на русский; проверка русской ошибки фильтра цены включена в `CatalogContentTest`.
- Зависимости: `npm audit --omit=dev` сообщил **6 уязвимостей (2 low, 4 moderate)** в зависимостях `shadcn`/`@shadcn/registry` (`deepmerge`, включая prototype poisoning) и `ts-morph` (`minimatch`, возможный DoS). Автоисправление не применялось: npm предлагает `--force` с major-обновлением `shadcn`; требуется отдельная проверка совместимого обновления/удаления ненужного runtime-пакета до production.
- 15 ноября выполнен локальный role-based browser smoke test на отдельных QA-аккаунтах для customer, manager, warehouse operator, administrator и super-administrator. Все пять учёток вошли через UI. Manager/Admin/Super Admin открыли CRM, каталог и склад; Warehouse Operator работал со складом, но UI и прямые API-запросы CRM/каталога получили отказ (403). Из-под Administrator смена роли также получила 403.
- В Super Admin browser session проверен новый экран `/admin/users`: список пяти локальных аккаунтов, поиск по имени/email и смена роли QA Customer на Manager с немедленным возвратом к Customer. Текущая роль восстановлена; оба изменения записаны штатным audit workflow. Проверены ширины 360/768/1024/1440 px; найденное на 360 px горизонтальное переполнение устранено мобильным видом карточек.
- В браузере клиент создал самовывоз-заказ; Manager назначил его на себя, добавил внутреннюю заметку, подтвердил и отменил заказ. Резерв после отмены освобождён (остаток снова 24, резерв 0). Клиентская история и детали заказа показали статус/состав, но не внутреннюю заметку. QA-заказ оставлен в локальной БД как отменённый.
- Warehouse Operator выполнил тестовое поступление +1 и сверку −1; журнал содержит обе записи, остаток восстановлен до 24. Полный suite не запускался в рамках этой ручной проверки; профильные backend suites — **35 passed, 269 assertions**. Очередь после клиентского заказа — 0 ожидающих/отложенных/зарезервированных и 0 failed.
- Browser smoke test подтвердил загрузку 3 demo-товаров, главного/промо-баннеров и отсутствие горизонтального переполнения каталога на 360/390/768/1280 px; Playwright отдельно проверяет, что кнопка фильтра доступна над мобильной нижней панелью. Ранее проверен переход «товар → добавить в корзину → корзина → checkout» на 360/768/1024/1440 px. Это не заменяет E2E-проверки всех экранов, ошибок и retry-сценариев.
- Дополнительно в браузере проверены товарная страница с canonical/Open Graph/JSON-LD и экран неизвестного URL; production HTTP 404 и реальное индексирование ещё требуют web-server/SEO проверки.

| Контакты `/admin/settings` | Администратор/супер-администратор меняет публичные телефон, WhatsApp, email, адрес, часы и соцссылки; футер показывает настроенные контакты и sitemap | Данные магазина пока не предоставлены — оставлены пустыми; нужны фактические контакты и проверка отображения на домене. |
| Статистика `/admin/analytics` | Администратор/супер-администратор задаёт период и видит показатели заказов, суммы, оплаты, покупателей, города, тренды, популярные страницы и недавние заказы с контактами; аналитика остаётся внутри приложения | Данные появляются после реального трафика/заказов. Требуются privacy/legal review, retention policy и нагрузочная проверка. |

### Действия, которые уже подключены

- Публичные: перейти на категорию/товар, отправить поиск, применить фильтры/сортировку, перейти между страницами, открыть аккаунт.
- Аккаунт: переключать login/register/forgot/reset; создать аккаунт с телефоном и без email; входить по телефону/email; добавлять/подтверждать email; сбрасывать пароль по email; сохранить профиль и выйти.
- Каталог-админ: переключить вкладки, создать/изменить/снять с публикации товар, добавить вариант/SKU, загрузить/удалить фото, создать/изменить/удалить категорию и баннер.
- Заказ: добавить в корзину, изменить количество/удалить позицию, войти или зарегистрироваться, заполнить доставку или самовывоз, отправить заказ и открыть подтверждение; customer order history доступна в аккаунте.
- Возвраты: клиент выбирает допустимые SKU/количество, подтверждает целую упаковку и отслеживает статусы; CRM связывается через WhatsApp и вручную меняет статус.
- Навигация: перейти по мобильным вкладкам магазина либо по desktop-сайдбару админки с учётом роли.
- CRM: искать/фильтровать заказы, открывать карточку, назначать сотрудника, фиксировать приватные заметки, согласовывать delivery fee, менять разрешённый статус и отмечать оплату/возврат; при подтверждении/отмене/отгрузке/самовывозе остаток обновляется транзакционно.
- Склад: искать SKU и остатки, принимать товар, сверять физическое количество и фильтровать журнал движений; уменьшение фактического количества ниже резерва блокируется.
- Пользователи: искать по имени/email/телефону, фильтровать по роли, менять сортировку/вид списка, выбирать и сохранять роль, листать результаты; сервер блокирует изменение собственной роли/последнего Super Admin и записывает изменения в аудит.
- Контакты и статистика: сохранить контакты в `/admin/settings`, открыть публичный footer и sitemap, выбрать период отчёта, сверить агрегированные просмотры и закрытые от покупателя данные заказов.
- Наличие формы/кнопки не является достаточным подтверждением полной готовности: нужен тест успешного, ошибочного, повторного и неавторизованного сценария.

## Приоритет работ до готовности полноценного магазина

1. **P0 — Сквозное качество CRM и склада:** расширить browser/E2E тесты на checkout, CRM и склад; проверить keyboard-доступность/роли и основные transitions.
2. **P1 — Складская надёжность:** PostgreSQL concurrency reserve/receipt/reconcile проверен в изолированной схеме; продолжить E2E и production-проверку уведомлений/worker, сохраняя закреплённый low-stock-порог.
3. **P1 — Возвраты:** провести юридическую проверку политики для Казахстана; определить ручной порядок приёма/оценки товара, фактического возврата денег и решения по пополнению остатков.
4. **P1 — Профиль и покупательские функции:** решить вопрос адресной книги/контактов; история заказов и безопасные детали уже реализованы.
5. **P1 — Полнота каталога:** наполнить иерархию реальными товарами/фото, проверить варианты изображений и полировать ошибки/пустые состояния; demo seeder для локального просмотра уже есть.
6. **P1 — Сквозное качество:** добавить Playwright для order checkout, CRM order workflow и склада; возвраты, мобильные вкладки и user-management уже имеют E2E. Выполнить keyboard/focus/labels и unit/component проверки на критичные сценарии.
7. **P1 — SEO:** dynamic sitemap/robots и product metadata реализованы; production Nginx routing и гарантированный HTTP 404 ещё требуют настройки и проверки.
8. **P2 — Уведомления:** базовая очередь/email/Telegram и consent flow реализованы; завершить production credentials, постоянный worker/monitoring и проверить очереди на окружении запуска.
9. **P2 — Аналитика и privacy:** собственная агрегированная статистика добавлена без сторонних tags/UTM; определить retention и проверить production-правила обработки заказов/privacy для Казахстана.
10. **P2 — Production readiness:** разобраться с найденными npm dependency advisories и совместимым обновлением зависимостей; оставшиеся PostgreSQL-specific constraints, права/секреты, Cloudinary, TLS/Sanctum на целевом домене, backups/restore, мониторинг, Ubuntu/Nginx/PHP-FPM deploy/rollback и тест нагрузки.

## Требования и решения, блокирующие запуск

- D-06 подтверждён владельцем 2026-11-11: доставка по Казахстану, полный адрес вводит покупатель, стоимость/сроки и самовывоз согласуются вручную через WhatsApp, фиксированной точки самовывоза нет. Автоматическая интеграция WhatsApp/перевозчика не входит в подтверждённое решение.
- D-07: возвратная политика требует юридической проверки для Казахстана до публикации/реализации.
- D-09: отзывы, купоны, скидки и customer-visible messages не утверждены; не включать самовольно.
- D-10 подтверждён: email о получении заказа отправляется на указанный email; статусные письма требуют отдельного согласия и содержат подписанную отписку; Telegram-сообщение по заказу создаётся только для нового заказа и не содержит контактов/адресов.
- D-17 подтверждён: общий порог 2 доступные единицы; показывать на складе и уведомлять Telegram только при переходе вниз, повторять после восстановления выше порога и нового пересечения.
- D-11: Google Ads/GA/GTM tags и UTM не входят в v1. По отдельному запросу владельца добавлена first-party статистика: дневные просмотры по типу страницы/slug и отчёты заказов внутри админки. Перед production определить retention и провести legal review хранения персональных/заказных данных.
- D-13: масштабы каталога/трафика не заданы; capacity нельзя считать принятой.
- Tax/vat treatment требует проверки до запуска, несмотря на решение не считать налог в v1.

## Демо-данные

Добавлен отдельный `DemoCatalogSeeder` для локального просмотра: 2 категории, 3 товара, 5 SKU-вариантов, тестовые остатки и активные hero/promo-баннеры. Он не подключён к обычному `DatabaseSeeder`, работает повторно без дублирования записей и намеренно запрещён в `production`. Картинки используют внешние demo URLs, не Cloudinary storage; реальные загрузки по-прежнему требуют серверной конфигурации Cloudinary.

Локальный запуск (из `backend/`):

```powershell
php artisan db:seed --class=Database\Seeders\DemoCatalogSeeder
```

Для текущего Windows PHP CLI, если `pdo_pgsql` не включён в `php.ini`, добавьте `-d "extension=<путь к PHP>\ext\php_pgsql.dll" -d "extension=<путь к PHP>\ext\php_pdo_pgsql.dll"` перед `artisan`.

## Итог

Основные модули каталога, аутентифицированного заказа, CRM, склада, уведомлений и базового процесса возвратов реализованы; demo-каталог загружается отдельным безопасным для локальной среды seeder. SQLite suite и текущие E2E/build проверки проходят, но PostgreSQL migration/concurrency повторно не проверены из-за отсутствующего локального PHP-драйвера. Это ещё не подтверждает production-готовность: остаются E2E-проверки checkout/CRM/склада, доступность, юридические решения и operational hardening. Нельзя считать систему готовой к запуску, пока критические acceptance criteria не пройдены и незакрытые решения не подтверждены.
